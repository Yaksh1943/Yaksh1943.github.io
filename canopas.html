01 / the challenge

Moving from Early Beta to Scale

At Canopas, our conversational AI features started with an initial cohort of 5,000 to 10,000 early users. As product adoption surged toward 50,000+ active users, challenges that were invisible in early testing suddenly became critical:

  • Silent Model Quality Regression: When updating prompt templates or testing newer foundation model versions, how do you verify that the changes don't subtly break existing user conversation personas or answer quality?
  • API Latency Under Traffic Spikes: Real-time voice and text chat cannot wait for synchronous third-party LLM calls, email dispatches, and analytics logging on the same thread.
  • Context Bleed & Memory: Users expect the AI assistant to remember key preferences and facts across multi-turn sessions without polluting prompt token limits.

02 / implementation

What I Engineered & Solved

1. Tooling via Model Context Protocol (MCP)

I helped design and implement feature workflows utilizing the Model Context Protocol (MCP). Instead of hard-coding brittle, ad-hoc integrations for each model, MCP gave us a standardized protocol to expose application state, live user context, and notification endpoints to the AI engine safely.

This powered dynamic, context-aware notifications and personalized interactions that felt continuous rather than robotic and disconnected.

2. "LLM-as-a-Judge" Automated Evaluation Pipeline

One of the biggest risks in production AI is silent prompt drift—you change one sentence in a prompt to fix one bug, only to cause five subtle hallucinations in other areas.

To solve this, I helped build an automated LLM-as-a-judge evaluation harness:

  • Curated a gold-standard benchmark dataset representing real user edge cases and multi-turn conversations.
  • Ran automated test suites before deploying prompt or model updates, having a judge model grade the candidate outputs against accuracy, tone consistency, and safety criteria.
  • Eliminated subjective "vibe checks" and gave the team objective confidence before releasing updates to 50K+ people.

3. Event-Driven Asynchronous Backend (FastAPI + AWS SQS)

To keep user-facing REST endpoints sub-100ms, I decoupled all non-critical operations from the HTTP request-response cycle:

  • Built high-performance FastAPI microservices with asynchronous task execution.
  • Wired AWS SQS message queues to manage heavy background jobs (media asset processing, long-term memory ingestion, transactional email notifications via SES).
  • Designed resilient PostgreSQL schemas with clean database indexing for fast profile lookups.
03 / reliability in production

"What Happened When Things Broke?"

Operating at 50,000+ users means failures happen daily. Here is how we engineered resilience into the system:

Case 1: Third-Party Model Outages & Rate Limit Spikes

Resolution: We implemented circuit breakers and fallback providers with exponential backoff. If our primary inference endpoint experienced rate throttling, requests seamlessly switched to secondary models with cached system prompt templates, preventing downtime for end users.

Case 2: Background Task Queue Overflows

Resolution: We configured Dead-Letter Queues (DLQs) on AWS SQS with CloudWatch alarm triggers. If a background notification or memory sync worker failed 3 times, the message was preserved in the DLQ for inspection rather than being dropped, allowing zero data loss during traffic spikes.

04 / takeaways

What I Took Away from Canopas

This experience solidified my engineering philosophy: real AI products are backend systems first, and model wrappers second. The models will constantly change, get cheaper, and get faster. But having solid background queues, automated evaluation baselines, and clean database schemas is what allows a product to scale sustainably.
