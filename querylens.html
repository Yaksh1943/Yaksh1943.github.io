01 / the problem

Why Naive Text-to-SQL Fails in Reality

Almost every AI engineer has tried prompting an LLM with "Here is my database schema, please write a SQL query for this user question." It works well in a 5-minute toy demo, but quickly falls apart when deployed against live production databases:

  • Ruinous Costs on Repeat Queries: Business users ask the same questions repeatedly (e.g., "What were yesterday's top orders?" or "Show monthly active users by country"). Re-running a multi-thousand-token prompt through an external LLM every single time burns budget for zero reason and forces users to wait 3 to 8 seconds.
  • Schema Confusion & Token Bloat: Real databases don't have 2 clean tables; they have 30 to 80 tables with complex foreign keys. Stuffing the entire schema into a prompt leads to hallucinations, column mismatch errors, and massive context overhead.
  • Malformed SQL & Silent Database Errors: Models regularly generate non-existent column names, mismatched brackets, or dialect-specific syntax errors. If sent directly to the database, the query fails with raw database error messages that leave non-technical users stranded.

02 / how it works

How QueryLens Processes a Question

To make natural language queries dependable, I designed a 5-step pipeline where every query is checked by code and syntax rules before anything touches the database:

Query Execution Lifecycle: Self-Healing AST Pipeline
STAGE 01 Intent Parsing Extract user intent
→
STAGE 02 Semantic Cache Skip LLM on match
→
STAGE 03 Hybrid Retrieval FastEmbed + BM25
→
STAGE 04 AST Validation sqlglot Guardrails
→
STAGE 05 Execution & Chart Recharts Visual

1. The Semantic Intent Cache (Speed & Efficiency)

Before touching any remote model, QueryLens computes an intent embedding of the user's question using local CPU embeddings (FastEmbed / BGE-small). If an identical or near-identical question was answered previously, the verified SQL is served directly from local cache.

The Result: Verified queries return near-instantly without making unnecessary remote API calls for recurring analytical questions.

2. Hybrid Schema Linking (High Accuracy)

When a query misses the cache, QueryLens does not dump the entire database catalog into the prompt. Instead, it runs a hybrid retrieval pipeline:

  • BM25 Sparse Search: Catches exact column names, table aliases, and business terms.
  • Dense Vector Search: Finds conceptually related tables based on semantic descriptions.
  • FlashRank Cross-Encoder Reranker: Reranks the top candidates on CPU with minimal latency, passing only the top 3–5 relevant tables into the LLM context.

3. Abstract Syntax Tree (AST) Validation with sqlglot

Once the LLM generates a SQL query, it is never executed directly. QueryLens parses the string into an Abstract Syntax Tree using sqlglot. This allows deterministic verification of:

  • Syntax validity against the exact dialect (PostgreSQL / MySQL).
  • Verification that every referenced table and column exists in the schema.
  • Strict safety checking: blocking any destructive queries (DROP, DELETE, ALTER, UPDATE).
03 / reliability & edge cases

"What Happens When It Fails?"

Building reliable software means planning for when things go wrong. Here is how QueryLens handles edge cases, hallucinations, and failures:

Case 1: The Model Generates Invalid SQL Syntax

What happens: sqlglot catches the parser error and extracts the precise line, token, and failure reason. Rather than showing an error to the user, QueryLens triggers a bounded self-healing reflection loop: the error trace is passed back with the original schema context. In testing, this automatic 1-turn repair resolves over 80% of common syntax slips without human intervention.

Case 2: The Question is Ambiguous or Data Doesn't Exist

What happens: If the question references concepts not present in the retrieved schema (e.g., "Show customer churn" when there is no subscription status column), the pipeline halts before generation and provides a clear, plain-English explanation of why the question cannot be answered, suggesting related tables the user might explore.

Case 3: Slow Execution or Table Locks

What happens: All database queries are executed over read-only connections with a strict 3,000ms timeout. If a query scans too many rows and times out, the process cleanly terminates, protecting database performance, and informs the user to apply a date filter or narrower scope.

04 / status & roadmap

Active Development & What's Next

QueryLens taught me that the best AI systems are 80% disciplined backend engineering and 20% model prompting. Safe parsers, local caching, and tight schema controls matter far more to user trust than having the newest massive model.

Current Status: Under Active Improvement v0.4 Beta

QueryLens is an active engineering project. Current areas of enhancement include:

  • Cross-Dialect SQL Transpilation: Expanding seamless AST translation between PostgreSQL, MySQL, ClickHouse, and SQLite.
  • Automated Chart Intelligence: Improving the heuristic engine that selects the best visualization type (line, stacked bar, scatter) based on returned SQL result shapes.
  • Multi-Tenant Vector Caching: Segregating cached intent vectors by tenant and user permission tiers.
